# PR-076: ViewModel for Controller detail page

Branch: pr-076-controller-detail-viewmodel
- Type: feature
- Complexity: medium
- Depends on: PR-075
- Priority: 2
- Coder: any

## Problem

The new Controller detail page (`/controller`) needs a unified view model aggregating health snapshot, live operations with start-from-here actions, CacheVault details, RoC temperature history reference (graph data lives in PR-080), RAID config table, scheduled tasks, full hardware identity (18 fields), and Buzzer control state. No such ViewModel exists today; controller data is split across `services/overview.py` (RoC, CV cards), `services/patrol_read.py`, `services/consistency_check.py`, and `storcli/parser.py` (hardware ID fields are in the raw snapshot, not exposed as a ViewModel).

## Scope

In scope (new module `services/controller_detail.py`):

1. `ControllerHealthSnapshot` dataclass:
   - `state: str` (OPTIMAL/WARNING/CRITICAL)
   - `summary_text: str` (e.g. "All systems nominal. 8/8 drives online. RAID 5 healthy.")
   - `roc_temperature_celsius: int | None`
   - `cv_capacitance_percent: int | None`
   - `bbu_status: str`
   - `memory_ecc_errors_total: int`
   - `errors_24h: int`
   - `uptime_text: str` (e.g. "7m 23s")

2. `LiveOperationCard` dataclass (used for Patrol Read / Consistency Check / BGI):
   - `name: str` (display name)
   - `mode_text: str` (e.g. "Auto mode. Interval 168h.")
   - `status_text: str` (e.g. "Idle. Last completed May 12 (8h 14m). Next in 4d 12h.")
   - `progress_percent: int | None` (None when not running)
   - `progress_eta_text: str | None`
   - `can_start: bool`
   - `can_stop: bool`
   - `can_change_mode: bool`
   - `start_url: str | None`
   - `stop_url: str | None`
   - `mode_url: str | None`

3. `CacheVaultDetail` dataclass:
   - `model: str` (e.g. "CVPM02")
   - `state: str`
   - `capacitance_percent: int | None`
   - `temperature_celsius: int | None`
   - `mfg_date: date | None`
   - `mfg_date_text: str` (e.g. "April 10, 2013 (~13 years old)")
   - `fw_cache_size_text: str` (e.g. "875 MB")

4. `RaidConfigRow` dataclass (one per VD):
   - `vd_id: int`
   - `name: str`
   - `raid_level: str`
   - `size_text: str` (e.g. "19.09 TB")
   - `state: str`
   - `state_severity: str`
   - `access: str`
   - `cache_policy: str` (e.g. "RWBD")
   - `strip_size_text: str` (e.g. "256 KB")

5. `ScheduledTaskRow` dataclass:
   - `name: str` (e.g. "Patrol Read")
   - `schedule_text: str` (e.g. "Every 168h (7 days). Next May 24, 18:00.")
   - `is_enabled: bool`
   - `configure_url: str | None`

6. `HardwareIdentity` dataclass (18 fields per mockup):
   - model, serial, revision, chip_revision, manufactured_date_text, rework_date_text
   - firmware_version, bios_version, driver_version
   - sas_address, pci_address, backend_ports
   - nvram_size_text, flash_size_text, memory_size_text, fw_cache_size_text
   - pending_images_count, alarm_buzzer_text

7. `BuzzerControlState` dataclass:
   - `current_setting: str` ("On", "Off", "Silenced")
   - `can_silence: bool` (true when On)
   - `can_disable: bool` (true when On or Silenced)
   - `can_enable: bool` (true when Off)
   - `silence_url: str`
   - `disable_url: str`
   - `enable_url: str`
   - `explainer_text: str` (constant copy from mockup)

8. `ForeignConfigState` dataclass:
   - `present: bool`
   - `drive_count: int`
   - `source_controller_serial: str | None`
   - `description_text: str`
   - `can_import: bool`
   - `can_clear: bool`
   - `import_url: str`
   - `clear_url: str`

9. `ControllerDetailViewModel` dataclass combining all above:
   - `page_title: str`
   - `page_subtitle: str` (e.g. "SN SV31207417. Updated May 20, 2026 18:42 CEST.")
   - `health: ControllerHealthSnapshot`
   - `live_operations: list[LiveOperationCard]`
   - `cachevault: CacheVaultDetail | None`
   - `roc_history_chart_url: str` (URL where frontend will fetch RoC chart; set up here for clarity)
   - `raid_config: list[RaidConfigRow]`
   - `scheduled_tasks: list[ScheduledTaskRow]`
   - `hardware: HardwareIdentity`
   - `buzzer: BuzzerControlState`
   - `foreign_config: ForeignConfigState`
   - `system_health: SystemHealthViewModel` (reuse from PR-075)
   - `updated_at: datetime`
   - `auto_refresh_seconds: int`

10. Loader function `load_controller_detail_view_model(session, *, settings, scheduler, collector_enabled, app_start_time, app_version) -> ControllerDetailViewModel`.

Out of scope:
- New endpoints. PR-083 will create `/controller` route consuming this VM.
- RoC temperature aggregation query (PR-080).
- Buzzer/foreign-config storcli wrappers and POST endpoints (PR-078, existing).
- Frontend templates (PR-083).

## Implementation notes

Reuse existing services where possible:
- `services/patrol_read.py` for patrol read state + scheduling info.
- `services/consistency_check.py` similarly.
- `storcli/parser.py` already parses HwCfg block (where Alarm and ROC Temperature live).

For `HardwareIdentity` 18 fields: most come directly from `ControllerSnapshot` columns. A few require parsing storcli raw JSON (sizes formatted from raw integers). Build a small mapper function `_build_hardware_identity(snapshot, raw_json)` that pulls each field with a default of "N/A" if missing.

For `BuzzerControlState`: read `alarm_state` from latest `ControllerSnapshot`. Map to can_* booleans per state. URL fields point to PR-078 endpoint paths even before PR-078 lands (the strings just exist; tests verify the URL strings, not that they 200).

For `ScheduledTaskRow.schedule_text`: storcli does not expose next-run timestamp directly. Compute from "interval=Xh" + "last_run_at" if available, else "Next: unknown".

The app start time is the simplest "uptime" source. If lifespan does not currently track it, add 3 lines: `app.state.start_time = datetime.now(UTC)` in startup. Loader reads `app.state.start_time` via Depends or request.app.state.

Default thresholds (RoC warning 95, RoC critical 105) come from Settings; do not hardcode.
