# PR-067: fix false-positive controller "Alarm" + health=critical

Branch: pr-067-controller-alarm-semantics
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: any

## Problem

Two visible UI bugs on the main dashboard arising from the same root cause: misinterpretation of `HwCfg.Alarm` from storcli.

`HwCfg.Alarm` on the LSI 9270CV-8i is the **buzzer-enabled configuration flag**, not the current alarm activation state. Possible values: `On` (buzzer is enabled and will sound on PD/VD failure) or `Off` (buzzer disabled). The default factory setting is `On`. It does NOT mean "an alarm is currently sounding".

The current code treats `Alarm != "Off"` as a critical condition. This results in:

1. **`controller_health` metric returns 2.0 (critical)** in production even though storcli reports `Controller Status: Optimal`, all 8 drives `Online`, BBU `Optimal`, RoC 74°C (well below warning at 95°C). Verified on production NAS 192.168.50.2.
2. **Main dashboard shows red "CONTROLLER: Alarm" tile** (the leftmost tile in the status strip) for the same reason.
3. **Event detector emits a warning event on every collector cycle** (every 5 minutes) because `current.controller.alarm_state != "Off"` always evaluates true. This pollutes the DB and the events page with false-positive entries. On a long-running production instance the DB has accumulated hundreds of these.

The fix has three parts: correct semantic interpretation of `Alarm` field, remove the false-positive event emission, and re-classify the dashboard tile to convey real meaning.

## Scope

In scope:
- Remove the `alarm_state != "Off" → critical` rule from `services/overview.py:derive_controller_health`. The controller health should be derived from real signals (PD aggregate, VD aggregate, RoC temperature, memory ECC error counters when available) - NOT from the buzzer config.
- Remove the corresponding event emission from `services/event_detector.py:check_controller_alarm` (lines around 188). Replace with: emit an info-level event ONLY when the `alarm_state` value transitions (e.g. someone runs `storcli set alarm=off`). The transition is rare and operator-initiated; logging it is informational, not warning.
- Update the dashboard tile labeled "CONTROLLER" from current behavior (red when Alarm != Off) to: green when controller is healthy, red when there are real problems. The tile should reflect `controller_health`, not the buzzer flag.
- Update the status_tile copy: rename "Alarm" value text to something semantically clear. Options:
  - Show the actual controller status text (`Optimal` / `Warning` / `Critical`) instead of "Alarm".
  - OR show "Buzzer: On/Off" on a separate small label inside the tile, with no color impact.
  - Decision: show controller status text. Buzzer config is a footer-level info, not main tile.
- Add a one-time DB cleanup migration that removes the historical false-positive `controller_alarm` warning events (those with category matching the misemitted ones from `event_detector.py:188`). This cleans up the existing pollution. Mark the migration with `is_destructive=False` because it only removes events the new code wouldn't have created.

Out of scope:
- Re-designing the dashboard tile layout. That is the dashboard redesign series, not this fix. This PR only changes the data feeding the existing "Controller" tile.
- Changing how `Alarm: On/Off` is parsed in `storcli/parser.py` or `storcli/models.py` - the field is still captured as-is. Only the interpretation changes.

## Implementation notes

The `Alarm: On` value comes from `HwCfg` section in storcli `/c0 show all J`. Verified on production: factory default. To turn off (would silence the physical buzzer): `storcli /c0 set alarm=off`. The dashboard should never display this as a critical condition.

Risk heading required because this changes `services/event_detector.py` (security perimeter per AGENTS.md doesn't strictly apply but changing event emission is operationally significant).

Migration 0008 is destructive of false-positive rows. Document in the PR description that this is one-time cleanup of bug-emitted events. Operators with custom downstream consumers of events should be warned, though for a single-operator homelab this is not relevant.

After merge, the production redeploy will:
- Stop emitting false-positive events going forward.
- Clean up existing false-positive events.
- Show green "Controller" tile when actually healthy.
- Drop `controller_health` Prometheus metric to 0.0 (optimal) when actually optimal.
