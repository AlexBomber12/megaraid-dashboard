# PR-068: DB perms 0600 + lock paths out of /tmp

Branch: pr-068-db-perms-lock-paths
- Type: bugfix
- Complexity: medium
- Depends on: none
- Priority: 1
- Coder: any

## Problem

Two related security findings from the L1+L3 audit, both about filesystem hygiene that could enable LAN-local DoS or info disclosure:

**Finding 1 - DB readable by `other`:**
`/var/lib/megaraid-dashboard/megaraid.db` is mode `0644` on production: world-readable. Any local user on the host (not just `megaraid` or `root`) can read the events table, audit log, maintenance state, and operator-action history. The DB does NOT contain plaintext passwords (only the bcrypt hash, and only via env file not DB), but it contains operator actions, drive serial numbers, and complete event history. For a homelab with a single user this is low actual risk, but it is wrong by principle and should be `0600`.

**Finding 2 - Lock files in `/tmp`:**
Default `Settings.collector_lock_path = "/tmp/megaraid-dashboard-collector.lock"`, similarly for `metrics_lock_path`. Any local user can pre-create these files (any owner, any mode). When `megaraid` user's daemon tries `os.open(..., O_CREAT | O_RDWR | O_NOFOLLOW)`, the file already exists and the daemon's `_validate_notifier_lock_file` check (correctly) rejects it because `st_uid != os.getuid()` → daemon raises RuntimeError → notifier/collector/metrics crash → service degradation.

The mitigation (`_validate_notifier_lock_file`) correctly prevents EXPLOITATION (no symlink follow, no foreign-uid hijack), but doesn't prevent **denial of service**. A local attacker can pre-create these files with their own uid and keep the daemon from acquiring the lock until either the file is removed (root cleanup) or the path is changed.

The fix for #2 is to move lock paths into `/var/lib/megaraid-dashboard/`, which is `0750` `megaraid:megaraid`. No other local user can write into it, so pre-create attack is impossible.

## Scope

In scope:
- Change defaults in `src/megaraid_dashboard/config.py`:
  - `collector_lock_path: str = "/var/lib/megaraid-dashboard/collector.lock"` (was `/tmp/megaraid-dashboard-collector.lock`)
  - `metrics_lock_path: str = "/var/lib/megaraid-dashboard/metrics.lock"` (was `/tmp/megaraid-dashboard-metrics.lock`)
- Update `scripts/install.sh` to NOT add these env vars to `/etc/megaraid-dashboard/env` unless explicitly overridden by the operator (so defaults take effect; same as `metrics_listen_address` is already handled).
- Update `deploy/megaraid-dashboard.service` to drop `/tmp` from `ReadWritePaths=` (only `/var/lib/megaraid-dashboard` needed). This also tightens systemd-level sandboxing.
- Update `install.sh` post-install step to chmod the DB to 0600 after first creation: `chmod 0600 /var/lib/megaraid-dashboard/megaraid.db`.
- Add migration-like Python check at app startup: if DB file exists and mode > 0600, log a warning and chmod it to 0600 (defensive, makes the fix self-healing for existing deploys).
- Update `INSTALL.md` and `TROUBLESHOOTING.md` to reference new paths.
- Update sudoers fragment if it references /tmp lock paths (probably doesn't).
- Update tests in `tests/test_services/test_scheduler.py` and `tests/test_web/test_metrics_*.py` for lock path fixtures using `tmp_path` (these already use tmp_path; no change to test logic, but verify they don't hardcode `/tmp`).

Out of scope:
- Migrating existing production lock files. After deploy, old `/tmp/megaraid-dashboard-*.lock` files remain on disk as orphans. They are not harmful (the daemon never references them again). Document in deploy notes: operator can `rm /tmp/megaraid-dashboard-*.lock` after restart.
- Removing the `_validate_notifier_lock_file` defensive check. Defense in depth: even if path changes, ownership/symlink checks stay.
- Changing the DB file path itself.

## Implementation notes

The startup chmod is defensive. It self-heals existing production deploys (the NAS at 192.168.50.2 currently has mode 0644). After this PR deploys, the first start applies chmod automatically.

The lock path change is a default-only change. Operators who override via env var keep their override. For production: the env file does NOT currently set `COLLECTOR_LOCK_PATH` or `METRICS_LOCK_PATH` (verified during deploy), so the new defaults take effect at next restart.

Risk heading required: this PR changes systemd unit, env defaults, and adds startup-time filesystem operations. The combination is operationally significant.

Defense-in-depth note: keep `_validate_notifier_lock_file` ownership and symlink checks intact even though the new path location makes them redundant for DoS prevention. They still protect against bugs in the install.sh (e.g., if it accidentally chmods data dir 0777, the check catches it).
