## Problem

After PR-067/068/069, unit + branch coverage is 100% and gated in CI. That covers code paths but does NOT cover **user-facing behavior**: the actual browser experience, JavaScript event handlers, form submission flows, multi-step wizards (e.g. drive replace), CSRF cookie + header pairing in real browser context.

Currently the only way to validate the UI works after a change is manual browser testing. With dashboard redesign series planned (PR-071..PR-078+), per-PR manual testing is unsustainable. Playwright e2e tests automate this.

Scope: install Playwright, write 8-12 high-value e2e scenarios covering the critical user flows, wire to CI as a separate stage that runs after unit tests pass.

## Scope

In scope:
- `tests/e2e/` directory with Playwright Python test files (`pytest-playwright` framework, not Node-style).
- Conftest with fixtures: `live_server` (starts the FastAPI app on a free port), `authenticated_page` (logs in via basic auth and returns a Playwright `Page` ready to use).
- 8-12 e2e scenarios covering the critical user flows (list below).
- `pyproject.toml` adds `pytest-playwright>=0.7` and `playwright>=1.50` to `[project.optional-dependencies].dev`.
- CI workflow updated to install Playwright browsers and run e2e tests as a separate job after the main `ci` job.
- README section explaining how to run e2e tests locally: `pytest tests/e2e/ --browser chromium`.

Out of scope:
- Visual regression testing (screenshots compared pixel-by-pixel). Too brittle for active dashboard redesign.
- Cross-browser (Firefox + WebKit). Chromium only for now; cross-browser added in a future PR if needed.
- Mobile viewport testing (Playwright supports it but mobile UI is itself a future PR-073+ deliverable, not stable enough to lock tests against).
- Load testing or accessibility testing.

## Critical user flows to cover

The 8-12 scenarios should be the most valuable for catching regressions in dashboard work. Suggested set:

1. **Unauthenticated request shows 401.** Visit `/`, no auth header. Expect 401 response + WWW-Authenticate.
2. **Basic auth login succeeds.** Provide correct credentials in `page.goto(url, http_credentials={...})`. Expect 200 HTML with dashboard markup. Check for known element (e.g., status strip).
3. **Wrong credentials are rejected.** Bad password → 401. After 5 failed attempts, expect 429 from rate-limit middleware.
4. **CSRF token round-trip works.** Issue a GET, capture `__Host-csrf` cookie, issue a POST to `/maintenance/start` with cookie + matching header. Expect 200. Repeat without header → 403.
5. **Maintenance start/stop happy path.** Click "Start maintenance" → form, submit with duration 5 minutes → success. Verify maintenance banner appears. Click "Stop" → banner disappears.
6. **Drive locate start/stop happy path.** Click locate-start button on drive 0:0 → confirmation dialog → submit → success toast. Click stop → confirmation → success.
7. **Drive replace wizard: serial mismatch rejected.** Step 1 form requires typing the drive serial. Type wrong serial → expect 409 + error message displayed inline.
8. **Healthz endpoint always returns 200 JSON without auth.** Hit `/healthz` from unauthenticated context. Expect 200 + JSON content type.
9. **Static assets served.** Visit `/static/css/app.css`. Expect 200 + CSS content type. No auth required.
10. **Events page renders timeline.** After login, navigate to `/events`. Expect at least one event row OR empty-state element.

Optional bonus (if scope allows):
11. **Mobile viewport renders without horizontal scroll.** Set viewport 360x640. Visit dashboard. Expect no horizontal scrollbar on body element.
12. **Drive detail page deep link.** Visit `/drives/0:0` directly. Expect 200 + drive info table.

    name: E2E
    runs-on: ubuntu-latest
    needs: ci
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

          playwright install --with-deps chromium
      - name: Run e2e tests

## Implementation notes

The `live_server` fixture is the trickiest part. Two approaches:

**Approach A - subprocess uvicorn:**
- Spawn `uvicorn --factory megaraid_dashboard.app:create_app --port 0 ...`.
- Parse stdout to find the actual port (uvicorn logs "running on http://...:N").
- Yield URL.
- Teardown: `kill` the process.
- Pros: real production-like server.
- Cons: env file setup is fiddly (need real `/etc/megaraid-dashboard/env`-like config); fragile parsing.

**Approach B - in-process via `uvicorn.Server` + asyncio task:**
- Build `Server(Config(app, host="127.0.0.1", port=0))`.
- Start as asyncio task in fixture.
- Yield URL after server is up.
- Pros: in-process; can patch settings via monkeypatch.
- Cons: not exactly production-like; some middleware might behave differently if process-state-shared.

Recommend **B**, with a clear caveat in test docstrings that "this is not 100% prod-like but matches main behaviors". Easier to set up env-like config via fixtures.

Authentication: use Playwright's `http_credentials` parameter on `browser.new_context(http_credentials={"username": "admin", "password": "..."})`. This adds the Authorization header automatically to every request from the context.

CSRF: Playwright handles cookies automatically. After first GET that issues `__Host-csrf`, subsequent POSTs need the header explicitly. Use `page.evaluate("document.cookie")` to read the cookie value, then `page.set_extra_http_headers({"X-CSRF-Token": value})` for the POST request.

Test data: each scenario should create its own minimal DB state. Use Alembic upgrade + direct ORM inserts. Don't share state between tests.

CI runtime: e2e tests are SLOW relative to unit tests (5-30s per test). 10 tests at 10s avg = 100s, acceptable. If creep above 3 minutes, split into a "fast smoke" subset that runs on every PR and a "full suite" that runs nightly or on merge to main.

Browser install: `playwright install --with-deps chromium` downloads ~150MB of binaries on first run. Cache the GitHub Actions browser binary path to avoid re-downloading per CI run.
