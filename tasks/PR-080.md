## Problem

The Controller detail page (per PR-076 ControllerDetailViewModel.roc_history_chart_url) needs a chart of RoC silicon temperature over the last 1h/24h/7d/30d. Data is already collected: each `ControllerSnapshot` includes `roc_temperature_celsius` since migration 0004 (PR-006 era).

What's missing is the aggregation query + endpoint to expose the data as a chart-ready time series. No new DB table per Q3 decision.

## Scope

In scope:

1. New module `services/controller_history.py` with:
   - `RocTemperaturePoint` dataclass: `captured_at: datetime`, `temperature_celsius: int`.
   - `RocTemperatureSeries` dataclass: `points: list[RocTemperaturePoint]`, `range_label: str`, `min_celsius: int | None`, `avg_celsius: int | None`, `max_celsius: int | None`, `current_celsius: int | None`, `warning_threshold: int`, `critical_threshold: int`.
   - `load_roc_temperature_series(session, *, range_hours: int, settings) -> RocTemperatureSeries`.

2. Aggregation strategy:
   - For `range_hours <= 24`: raw 5-minute samples (288 points max).
   - For `range_hours > 24 and <= 168`: hourly average (168 points max for 7d).
   - For `range_hours > 168`: daily average (30+ points).
   - Use SQL `strftime` for grouping; portable across SQLite. Verify the query is efficient via `EXPLAIN QUERY PLAN`.

3. New GET endpoint in `web/routes.py`:
   - `GET /controller/roc-history` named `controller_roc_history`.
   - Query parameter: `range_hours: int` (default 24, allowed: 1, 24, 168, 720).
   - Returns JSON with the RocTemperatureSeries shape (for Chart.js consumption).
   - Auth required (existing middleware).
   - Cache-Control: `private, max-age=30` (matches polling interval).

4. The endpoint URL string is referenced by PR-076 ControllerDetailViewModel.roc_history_chart_url; this PR makes it concrete.

Out of scope:
- New DB table (decided B in Q3 - reuse controller_snapshots).
- Frontend Chart.js setup (PR-083).
- Per-drive temperature history (already exists in drive_history.py).
- Aggregation other than RoC (memory ECC trends etc. are separate).

## Implementation notes

The aggregation strategy is intentionally simple. For 24h: raw points. For longer ranges: SQL group by `strftime('%Y-%m-%d %H', captured_at)` for hourly, `strftime('%Y-%m-%d', captured_at)` for daily. Average roc_temperature_celsius within each bucket.

Watch out for: SQLite timezone handling. Timestamps in DB are UTC; if grouping uses local time we get duplicate hours during DST. Use UTC strftime explicitly.

For min/avg/max/current:
- min/max: aggregate over the displayed points.
- avg: aggregate over the displayed points (not raw, so hourly-bucket avg of avgs is acceptable approximation for chart context).
- current: latest raw sample regardless of range (always the most recent collector cycle's value).

For range validation: a small enum/set of valid values (1, 24, 168, 720) makes typo-protection easy. Reject other values with 422.

Cache-Control: 30 seconds matches the dashboard polling interval. Stale-while-revalidate would be nicer but adds complexity; basic max-age is enough for now.

## Risk

Read-only endpoint. New SQL aggregation query needs index check: `controller_snapshots.captured_at` should already have an index (verify via migration 0001 history). If not, this query will be slow on large DBs.
