# PR-093: Fix collector "never" in status bar (single source of truth from metric)

Branch: pr-093-fix-collector-last-run-source
- Type: bugfix
- Complexity: low
- Depends on: PR-092
- Priority: 2
- Coder: any

## Problem

The main page bottom status bar shows Collector "never", even though the collector runs successfully every 5 minutes in production.

Confirmed in production:
- Live process logs show `collector_cycle_metrics_recorded ... successful=True` every 5 minutes.
- The Prometheus gauge `megaraid_collector_last_run_timestamp` (exposed on the metrics port) holds a fresh, correct timestamp.
- BUT the status bar reads `scheduler.get_last_collector_run_at()` which returns `None`, rendered by `_format_relative_time(None)` as "never".

The collector cycle (`scheduler.py` `_run_collector_cycle`, success branch) updates BOTH `COLLECTOR_LAST_RUN_TIMESTAMP.set(time())` AND the module-level global `_LAST_COLLECTOR_RUN_AT` via `_record_last_collector_run_at(...)`. Despite running in a single uvicorn process, the web request handler reads the module global as `None` while the Prometheus gauge is fresh. The two are out of sync: the gauge is reliable, the module global is not visible to the request handler.

Rather than chase the exact namespace/context reason the module global is not visible (APScheduler job execution context vs request handler), this PR makes `get_last_collector_run_at()` read from the SAME source that already works: the Prometheus gauge. One source of truth eliminates the desync by design, regardless of the underlying cause.

## Scope

In scope:

1. Change `services/scheduler.py` `get_last_collector_run_at()` to derive its value from the `COLLECTOR_LAST_RUN_TIMESTAMP` Prometheus gauge instead of the separate module global `_LAST_COLLECTOR_RUN_AT`:
   - Read the gauge's current value (a Unix timestamp float).
   - If the value is 0.0 or unset (the metrics module initializes it to 0.0), return `None` (collector has not completed a successful cycle yet).
   - Otherwise convert the Unix timestamp to a timezone-aware UTC `datetime` and return it.

2. Keep writing the gauge in the collector cycle exactly as today (no change to the write path; the gauge is the working source).

3. Decide the fate of the now-redundant module global `_LAST_COLLECTOR_RUN_AT` and `_record_last_collector_run_at`:
   - If nothing else reads the global after this change, remove both the global and `_record_last_collector_run_at`, and remove the `_record_last_collector_run_at(...)` call in `_run_collector_cycle`. Grep first to confirm no other reader.
   - If removal expands the diff or risks other tests, leave them in place but unused for this PR and note them for a later cleanup. Prefer removal if clean.

## Reading the gauge value

`prometheus_client` Gauge exposes its current value. Read it via the documented-enough internal `gauge._value.get()`, or more robustly via `gauge.collect()[0].samples[0].value`. Wrap in a small helper `_read_collector_last_run_timestamp() -> float` so the access point is single and testable. Handle the case where the gauge has no samples defensively (return 0.0).

## Implementation notes

The collector cycle currently does, on success:

```
COLLECTOR_LAST_RUN_TIMESTAMP.set(time())
_record_last_collector_run_at(datetime.now(UTC))
```

After this PR, the second line is redundant (the reader uses the gauge). If removing it, also remove the global and the recorder function. If keeping for safety, that is acceptable but document it as dead code for a future sweep.

Timezone: the gauge stores `time()` (Unix epoch seconds, UTC). Convert with `datetime.fromtimestamp(value, tz=UTC)`. Ensure the returned datetime is timezone-aware so `_require_aware_utc` downstream does not reject it.

The 0.0 sentinel: `web/metrics.py` initializes the gauge to 0.0. Treat 0.0 (and any value below a sane epoch floor, optionally) as "never ran" -> None.

## Risk

Changes the read path of collector-last-run from a module global to the Prometheus gauge. The write path is unchanged and already proven to work in production. The main risk is timezone handling (naive vs aware) and the 0.0 sentinel; both are covered by tests.

Smoke test after merge: with the collector having run at least once, the main page status bar shows "Collector just now" (or "N min ago"), not "never". The Prometheus metric value and the status bar now agree because they share one source.
