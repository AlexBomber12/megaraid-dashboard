# PR-078: Buzzer control endpoints (silence/disable/enable)

Branch: pr-078-buzzer-control-endpoints
- Type: feature
- Complexity: low
- Depends on: PR-077
- Priority: 2
- Coder: any

## Problem

The controller has a physical buzzer that sounds on PD/VD failure events. For a homelab dashboard the operator needs quick access to silence a sounding alarm without changing the buzzer's permanent on/off setting. Use case: the buzzer goes off at night, the operator needs one click to silence so the family can sleep without disabling the buzzer entirely.

The new Buzzer Control section (per PR-076 ControllerDetailViewModel.buzzer) needs three POST endpoints. Currently there are no storcli wrappers for alarm management and no endpoints for it.

## Scope

In scope:

1. New storcli command builders in `services/drive_actions.py`:
   - `build_alarm_silence_command() -> list[str]` returning `["/c0", "set", "alarm=silence"]`
   - `build_alarm_disable_command() -> list[str]` returning `["/c0", "set", "alarm=off"]`
   - `build_alarm_enable_command() -> list[str]` returning `["/c0", "set", "alarm=on"]`

2. New POST endpoints in `web/routes.py`:
   - `POST /controller/buzzer/silence` named `controller_buzzer_silence`
   - `POST /controller/buzzer/disable` named `controller_buzzer_disable`
   - `POST /controller/buzzer/enable` named `controller_buzzer_enable`

3. Each endpoint:
   - Requires CSRF token (existing middleware handles this).
   - Requires basic auth (existing).
   - Calls the corresponding storcli command via the existing runner.
   - Records an audit event (category `controller_buzzer_silence`, etc., severity `info`) using the `_record_operator_action_or_500` helper from PR-069.
   - Returns 303 redirect to `/controller` on success.
   - Returns 502 on storcli error with the documented error body.
   - Returns 500 on audit failure (PR-069 unified contract).

4. Each endpoint emits an event with:
   - Category: matches the action (`controller_buzzer_silence` / `controller_buzzer_disable` / `controller_buzzer_enable`).
   - Severity: `info`.
   - Summary: human-readable (e.g. "Buzzer silenced by operator admin").
   - Operator username: from request.

Out of scope:
- Frontend (PR-083 templates).
- Visual indicator when buzzer is sounding (storcli does not expose "currently sounding" state on this firmware; PR-076 noted this; we silence blindly and trust the operator).
- Auto-silence on alert email send (separate feature, not requested).

## Implementation notes

The storcli docs confirm `/cx set alarm=silence|off|on` is the canonical syntax. Verify on production by running `sudo storcli64 /c0 set alarm=silence` manually first if uncertain.

Audit event categories should match the naming style of existing categories (e.g. `drive_locate_start`, `controller_patrol_read_start`). Add to the audit category enum if such a registry exists.

The pattern for these endpoints is identical to existing locate/patrol_read endpoints. Copy structure, replace storcli command, replace audit category. Do not invent new patterns.

These endpoints are CSRF-protected and require auth, so the existing `_whitelist.py` is NOT touched.

## Risk

This PR adds three mutating endpoints to the security perimeter. Risk heading required.

Storcli `set alarm=silence` is destructive in the sense that it changes runtime state, but it does NOT change persistent config (set alarm=off does that). Document this distinction in the audit event summary.
