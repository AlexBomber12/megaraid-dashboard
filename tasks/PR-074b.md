## Problem

PR-074 subdivision chunk **b**. PR-074a installed Playwright infrastructure. This PR adds the auth-flow scenarios: unauthenticated 401, successful login, wrong credentials, rate-limit at 5 failed attempts.

These are the simplest e2e scenarios (no DB state setup beyond defaults from PR-074a) and exercise the security perimeter.

## Scope

In scope:
- `tests/e2e/test_auth_flow.py` with 4 tests covering 3 scenarios:
  1. **Unauthenticated request shows 401.** GET / via Playwright page.request (no http_credentials in context). Assert status 401 and `www-authenticate` header present.
  2. **Basic auth login succeeds.** Create new context with `http_credentials={"username": test_admin_creds["username"], "password": test_admin_creds["password"]}`. GET /. Assert 200 and response.text contains a known marker (e.g. `<title>` containing "MegaRAID" or status strip element selector).
  3. **Wrong credentials rejected.** Context with `http_credentials={"username": "admin", "password": "wrong-password"}`. GET /. Assert 401.
  4. **Rate limit triggers at 5 failed attempts.** Loop 6 times: GET / with wrong creds. Assert first 5 return 401, 6th returns 429 (rate-limit).
- New fixture `authenticated_page` in `tests/e2e/conftest.py` for use by later sub-PRs (c, d). Creates a Playwright context with `http_credentials` set to valid test admin creds, returns a Page.

Out of scope:
- CSRF, maintenance, locate scenarios (PR-074c).
- Replace wizard, static, events scenarios + CI workflow (PR-074d).

## Files to create

`tests/e2e/test_auth_flow.py`:
```python
import pytest

@pytest.mark.asyncio
async def test_unauthenticated_returns_401(live_server, page):
    response = await page.request.get(f"{live_server}/")
    assert response.status == 401
    headers = response.headers
    assert "www-authenticate" in {k.lower() for k in headers}

@pytest.mark.asyncio
async def test_login_succeeds_with_correct_credentials(live_server, browser, test_admin_creds):
    context = await browser.new_context(
        http_credentials={
            "username": test_admin_creds["username"],
            "password": test_admin_creds["password"],
        }
    )
    page = await context.new_page()
    response = await page.goto(f"{live_server}/")
    assert response.status == 200
    content = await page.content()
    assert "MegaRAID" in content or "megaraid" in content.lower()
    await context.close()

@pytest.mark.asyncio
async def test_wrong_password_rejected(live_server, browser):
    context = await browser.new_context(
        http_credentials={"username": "admin", "password": "wrong"}
    )
    page = await context.new_page()
    response = await page.request.get(f"{live_server}/")
    assert response.status == 401
    await context.close()

@pytest.mark.asyncio
async def test_rate_limit_triggers_at_fifth_failure(live_server, page):
    # 5 failed attempts allowed by default; 6th hits rate-limit
    last_status = None
    for i in range(6):
        response = await page.request.get(
            f"{live_server}/",
            headers={"Authorization": "Basic YWRtaW46d3Jvbmc="},  # admin:wrong
        )
        last_status = response.status
        if i < 5:
            assert response.status == 401, f"attempt {i+1} should be 401"
    assert last_status == 429, "6th attempt should be rate-limited"
```

## Implementation notes

The rate-limit test depends on PR-068/070 era config values. Default per-minute attempts is 5 (verified during deploy: `AUTH_RATE_LIMIT_PER_MINUTE=5`). The test must run with these defaults; if a future config change raises the limit, this test needs an update.

The rate-limit attempt counts client IP. Since all test requests come from 127.0.0.1, they share one bucket. Tests must NOT share state across test functions; either:
- Each test uses a fresh `live_server` (session-scoped is wrong for this test).
- The test triggers rate-limit and verifies behavior within its own function scope.

Choose the second approach: the rate-limit test creates 6 attempts in a tight loop within one test. After this test, the bucket has 5 entries that will expire in 60 seconds. Other tests in the session that rely on 401 vs 200 behavior need to not have been affected (the unauthenticated test runs in <60s and uses correct fail counter; should be fine since it makes 1 request).

If test ordering becomes brittle, mark the rate-limit test with `@pytest.mark.last` or move to a separate file that runs last.

For the login test: the response body must contain SOME identifying marker. The current dashboard renders `<title>MegaRAID Dashboard</title>` or similar. If the redesign changes this, update the assertion in a follow-up PR.
